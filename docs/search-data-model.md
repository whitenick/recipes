# Search Data Model — `data/recipes.json`

The committed corpus (regenerated by `node build.js`, see `build.js`) is the
single source of truth for the search service (Stage 2, Meilisearch). This file
is the contract between the build pipeline and the index: any field the search
bar needs to match, filter, or sort by must be present here in a normalized form.

---

## 1. Record schema

Each item in `data/recipes.json` is one recipe object:

| Field | Type | Source | Indexing role |
|---|---|---|---|
| `id` | `string` | `slugify(title)` | Document id (Meilisearch `primaryKey`) |
| `title` | `string` | H1 / filename | **Searchable** |
| `description` | `string \| ""` | `## Description`, `## Overview`, or first prose paragraph | **Searchable** |
| `categories` | `string[]` | Auto-detected in `build.js` | **Searchable** + **Filterable** (facet) |
| `ingredients` | `string[]` | `## Ingredients` / `## Mise en Place` lists | **Searchable** |
| `meta.prepTime` | `string \| null` | `**Prep Time:**`, `- **Prep Time**:` | Display only |
| `meta.cookTime` | `string \| null` | same pattern | Display only |
| `meta.totalTime` | `string \| null` | `**Total Time**` / `**Timeline**` | Display only |
| `meta.servings` | `string \| null` | `**Servings**` / `**Yield**` | Display only |
| `meta.prepTimeMinutes` | `number \| null` | derived from `prepTime` | **Filterable** (facets) |
| `meta.cookTimeMinutes` | `number \| null` | derived from `cookTime` | **Filterable** |
| `meta.totalTimeMinutes` | `number \| null` | derived from `totalTime` | **Filterable** |
| `meta.servingsMin` | `number \| null` | derived from `servings` | **Filterable** |
| `meta.servingsMax` | `number \| null` | derived from `servings` | **Filterable** |
| `source` | `string \| null` | `Source: https://…` line | — (not indexed) |
| `dateAdded` | ISO `string` | file mtime | **Sortable** (Recent Recipes) |
| `content` | `string` (raw markdown) | source file | **Excluded from the index** — kept only for the site's detail view |

### Recommended Meilisearch attribute assignment (Stage 2)

- `searchableAttributes`: `title`, `description`, `ingredients`, `categories`
- `filterableAttributes`: `categories`, `meta.prepTimeMinutes`, `meta.cookTimeMinutes`,
  `meta.totalTimeMinutes`, `meta.servingsMin`, `meta.servingsMax`
- `sortableAttributes`: `dateAdded`
- `primaryKey`: `id`
- Index only a projection: send records **without** the `content`/`filename`/
  `subdir` fields unless a future stage explicitly needs them.

## 2. Decisions (recorded for this issue)

1. **Searchable vs filterable.** Free-text matching lives on `title`,
   `description`, `ingredients`, and `categories` (what users type: a dish, an
   ingredient, a category word). Faceted narrowing lives on `categories` and the
   numeric `meta` facets. `source` and `dateAdded` are metadata, not search
   text.
2. **Categorization stays build-driven (auto-detected).** We keep the existing
   `detectCategories` heuristics in `build.js` and surface the auto-detected
   list as the `categories` facet. No curated taxonomy or manual per-recipe
   override was introduced — that keeps the corpus regenerable from markdown.
   Known cost: occasional false positives (documented in
   `RECIPE_PIPELINE.md §3 Limitations`). Query filters map `categories=…` →
   `categories = "<name>"` in Meilisearch.
3. **Debris policy.** `meta` time/serving values are scrubbed of flattening
   artifacts (`45 mins Cook Time`, `6 Hr Serves`, `1 hour 45 minutes Yield`,
   `Step 1`, `Calories`, ratings, `N` placeholders) and unit-normalized to
   `mins`/`hr`(`s`). Descriptions never carry the `- **Prep Time**: …` meta
   blocks, `Cook Mode`, or `Jump to Recipe` boilerplate. Ingredient lists drop
   cook-mode lines, `1/2`-style rating fragments, and title echoes.
4. **Numeric facets are best-effort, additive, and never contradict the text**
   `prepTimeMinutes` etc. are derived only when a value actually parses; an
   unparseable value keeps its display text and a `null` facet. Ranged servings
   yield `servingsMin`/`servingsMax`; a single count fills both. This lets Stage
   2 add "under 30 minutes" filters without re-parsing anything.
5. **`dateAdded` is the file mtime.** Rebuilding is therefore stable only as
   long as the vault's file mtimes are unchanged; touching a source file makes
   it appear "recent" on the site. This is pre-existing behavior, preserved.

## 3. Rebuild & reindex path

The corpus is generated, never hand-edited (`data/recipes.json` is build
output). To rebuild from the Obsidian vault:

```bash
# Vault path is read from env when set, else the historical default.
RECIPES_DIR="/path/to/.../Recipes" node build.js   # → data/recipes.json
node --test                                        # → corpus invariants
```

The one-step deploy path (`bash update.sh`) runs `node build.js` and pushes,
which is all the site needs for now. Reindexing Meilisearch is a Stage 2 /
WILS-4 concern; the seed document is the cleaned record above.

## 4. Known caveats (accepted for this stage)

- **Duplicate `id`s** — three titles occur twice in the vault
  (`chicken-piccata`, `french-onion-soup`, `jambalaya`), producing colliding
  slugs pre-existing in the corpus. Because `id` is the Meilisearch primary key
  and the site's favorites key, duplicates overwrite in the index. Fixing this
  is a source-data change (rename/merge one of each pair), deliberately out of
  scope for the data-model stage.
- **Numeric facets are best-effort** for unusual values (e.g.
  `Makes one 9×13-inch sheet` → `servingsMin/Max` reflect the digits found).
  Display text remains the human-facing truth.
- **Empty descriptions** are legal (`""`); cards render without a blurb.
- **Scrape artifacts still on `title`/`content`** — some slug-style filenames
  (e.g. `allrecipes-com-recipe-…`) keep scrape-y names. They remain searchable
  via their text; no curation pass was done beyond the cleaning above.
